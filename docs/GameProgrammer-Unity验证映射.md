## 一、先把两件事分清楚

| | game-programmer 书单 | 你的 Unity 项目 |
|---|---|---|
| 回答什么 | **学什么**（知识地图，12 域、上百本书） | **怎么验证**（能不能做出来、跑起来） |
| 形态 | 2016–2018 年绘制，最后一次更新 2019-01，无后续维护 | 实时可运行 |
| 技术栈 | C++ / DirectX / OpenGL / 自研引擎导向 | C# / Unity 组件引擎 / URP |
| 进度机制 | **没有**，需要自己定义 | 用 `MOD-` 和 `GP-` 标记可统计 |

**两个必须知道的事实**：

1. 书单里的 Unity 书是 **Unity 5 时代**（《Unity5实战》《Unity 5 Game Optimization》《Unity人工智能游戏开发》第2版）。这恰恰是你的机会：用 2022 LTS 的新功能把旧例子重做一遍，能直接看出"哪些做法已经被新 API 取代"。
2. 书单是 **C++ / 底层引擎导向**，而 Unity 是 **C# 组件引擎**。不是所有域都能在这个项目里实机验证——硬做会得到假掌握。所以下面把 12 个域分成三类。

**三类策略**：

- **A 实机验证**：理论能直接用 C# 在 Unity 里复现 → 写可运行 demo，这是真验证。
- **B 封装层观察**：Unity 替你做了底层，只能验效果、不能验实现 → 验收改成"能解释 Unity 封装了什么"，别写"已实现引擎"。
- **C 不在此项目**：语言/平台不对等 → 阅读级，或另开 C++ 原生工程；不冒充验证。

## 三、A 类四个域，值得优先验证

这四个在 Unity 里投入产出比最高——因为理论能直接变成可运行的东西，而不是"读过"。

### GP-04 游戏数学 — 最划算的一个

**为什么在这里验证**：Unity 的 Transform 系统就是这套数学的活教材，四元数、矩阵、坐标系转换全是现成的。

> **学完你能得到什么**
> - **能做出**：物体绕任意轴旋转、朝向目标平滑插值、一条可控曲线；换坐标系后结果一致。
> - **能解释**：四元数为什么没有万向锁；矩阵乘法顺序为什么影响结果。
> - **能迁移**：摄像机跟随、弹道计算、程序化生成都靠这套。

**怎么做**：读《3D Math Primer》对应章节 → 在 `MOD-004` 样条场景里写旋转/插值 → 对比 Euler 与 Quaternion 在极端角度的表现 → 留一张对比截图。

**验收**：能用白板画出一次旋转对应的四元数运算，且代码跑出来的结果和推导一致。

### GP-10 游戏 AI — 和你项目名最贴合

**为什么在这里验证**：书单第 10 域专门有一本《Unity 人工智能游戏开发》，但那是 Unity 5 时代的——用 2022 的 AI Navigation 包重做，落差就是学习收获。

> **学完你能得到什么**
> - **能做出**：一个 NPC 会绕障追击（MOD-002），再叠加一层 FSM：巡逻→发现→追击→丢失目标→回巡逻。
> - **能解释**：NavMesh 只解决"怎么走"，不解决"去哪"；行为树和 FSM 分别适合什么规模。
> - **能迁移**：塔防、RTS、NPC 对话触发都是同一套分层。

**怎么做**：先完成 `MOD-002` 的点击移动 → 写一个 `StateMachine` 脚本管理 NPC 状态 → 让 NavMeshAgent 只负责每个状态里的移动 → 录一段状态切换的 Console 日志。

**验收**：NPC 行为分层清晰，你能指出"哪段是导航、哪段是决策"。

### GP-03 软件开发 — 用数据取代口号

> **学完你能得到什么**
> - **能做出**：同一个功能的两版实现（一版堆在一个类里、一版用状态模式＋对象池），Profiler 各测一次。
> - **能解释**：为什么对象池能降低 GC 频率——用内存快照证明，不靠背概念。
> - **能迁移**：接手烂代码时知道先改哪里、怎么证明改好了。

**验收**：两份 Profiler 截图 + 一段你自己的结论；说不出数据就等于没验证。

### GP-09 物理与动画 — 完整可复刻

> **学完你能得到什么**
> - **能做出**：用 C# 复刻《代码本色》里的一个转向行为（seek / flee / wander），和 Unity 内置方案对比。
> - **能解释**：碰撞检测的 broadphase 与 narrowphase 分工；为什么 PhysicMaterial 的摩擦系数这样设。
> - **能迁移**：任何"群体运动 / 碰撞响应"问题都能自己建模。

**验收**：你的复刻版本能跑出和书上一致的行为轨迹。

## 四、B / C 类怎么写才不算假掌握

**B 类的验收话术要改**：不写"实现了渲染管线"，写"验证了 URP 在开启 TAA 后边缘锯齿的变化，并解释了它用历史帧累积的原理"。**验效果 + 能解释封装**，就是 B 类的合格证据。

**C 类明确划出去**：C++ 语言全书、DirectX/OpenGL/Vulkan、PBRT 离线渲染、自研脚本引擎与 GC 实现——这些要真正掌握，得另开 C++ 原生工程，不是这个项目的目标。写进笔记时标注"阅读级，未实机验证"。

**旧书的处理原则**：书单里所有 Unity 5 时代的书，读的时候同步记一笔"这个做法在 2022 LTS 里被什么取代"。这条笔记本身就是一个验证产物。

## 五、双轨进度怎么记

项目里有两条线，**不要混用标记**：

- `// @trace MOD-00X` — 引擎功能线：2022 LTS 的新功能（10 个模块）
- `// @verify GP-0X` — 理论验证线：书单知识域的验证点（11 个域）

B / C 类不写脚本的，在 `Evidence/` 建 `GP-0X-笔记.md`，写清"验了什么效果/解释了什么封装/哪些没验"，同样计为完成。
